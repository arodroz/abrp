# 13. Telemetry Profile format: tprof-1 envelope, OBDb-aligned decode core

Date: 2026-09-01
Status: Accepted
Wayfinder ticket: https://github.com/arodroz/abrp/issues/74

## Context

The live-telemetry effort (map #72) wants any EV to be "a profile file away", with
community datasets standing in for physical validation of cars we don't own. The
dataset audit (docs/research/obd-datasets.md) found one corpus shaped like that goal —
OBDb's per-vehicle `signalsets/v3` JSON — but with hard limits: the schema is **closed**
(`additionalProperties: false` throughout) and cannot express structured pack-variant
constants (the Ioniq 5's 58/72.6/77.4 kWh split exists only as free prose), ISO-TP
flow-control parameters beyond one boolean, or our validation-tier metadata. Its decode
core, though, is battle-tested across hundreds of vehicles, its per-command `din`/`dout`
covers extended-session prerequisites, and its test cases are recorded multi-frame
responses with expected decoded values — 97 % command coverage on the Ioniq 5.

Community sources also demonstrably disagree on byte conventions: our imported
implementation guide places the `220101` SoC at payload byte 6, while OBDb's recorded
vector puts the decoded value (0x8E ÷ 2 = 71 %) at byte 7 — and labels it "dashboard"
where the guide says true BMS SoC. Transcribed tables cannot be trusted; recorded
vectors adjudicate. OBDb data is CC-BY-SA-4.0; this repo is MIT.

## Decision

1. **Our own envelope format, `tprof-1`** (JSON, a `format` field like `tlog-1`), not
   OBDb's schema with sidecars and not a from-scratch schema. A profile carries: the
   vehicle tag(s) it serves; the ECU/command list (headers, UDS request, session
   prerequisite, poll cadence); per-signal decode rules; and the extension blocks OBDb
   cannot express — **pack variants** (structured per-variant constants: populated cell
   count, usable/nominal capacity, remaining-energy ceiling), **canonical mapping**,
   **validation tier** (`car-validated` / `vector-validated` / `paper`) with provenance,
   and optional engine hints (flow-control overrides, timeouts).
2. **The decode core adopts OBDb's field semantics near-verbatim** (`bix`, `len`,
   `sign`, `add`, `mul`, `div`, `unit`, `map`, null/override ranges): the importer stays
   mechanical, community knowledge transfers, and their test vectors run against our
   decoder without semantic translation. Exact key set and the bit-index origin
   convention are finalized by the decoder ticket (#77) **with the recorded vectors as
   arbiter** — the byte-6-vs-7 conflict above is settled empirically there, not by
   picking a table to believe.
3. **Canonical Signals.** The engine owns a small fixed signal vocabulary — BMS SoC,
   Display SoC, pack current, pack voltage, cell voltages, module temperatures, SoH,
   remaining energy, cumulative charge/discharge energy and charge, 12 V voltage,
   odometer — and every profile maps its native signals onto it; unmapped signals stay
   readable as raw named extras. The app consumes canonical signals only: swapping the
   profile never touches app code.
4. **Two licensing lanes.** `data/profiles/` holds first-party profiles — authored from
   facts (DIDs, offsets, scalings are not copyrightable), never copied files — under the
   repo's MIT license. `data/imported/obdb/` holds anything imported — CC-BY-SA-4.0 with
   its own LICENSE file and NOTICE.md attribution — regenerated by tooling, never
   hand-edited. Import now: the Ioniq 5 **test vectors** (the decoder ticket needs them
   for vector validation). Bulk multi-vehicle signalset import is deferred until
   something consumes it; 60 % of OBDb's BEV repos are empty stubs.
5. **Vector validation is defined against our decoder**: a profile earns
   `vector-validated` only when the recorded responses decode to the expected values in
   our replay harness — OBDb's own CI passing is not our tier.

## Consequences

- The decoder (#77) builds against this: load tprof-1, poll, decode, apply pack-variant
  truncation, emit canonical signals over FFI.
- The importer is one-way and mechanical; OBDb schema drift is absorbed at import time,
  not runtime. Our first-party profiles stay MIT and independent of OBDb's evolution.
- The EV6 paper profile is authored (E-GMP shared decoding), not imported, proving the
  format without the import pipeline.
- OBDb's request side is metadata, not vectors — request-byte correctness (headers, FC
  setup) remains proven by our own engine replay fixtures and the driveway smoke.
